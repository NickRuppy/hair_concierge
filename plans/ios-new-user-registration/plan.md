## Auth binding refinement before implementation
The provider's numeric OTP is email-scoped, so merely recording attempt email is insufficient when multiple quiz submissions race. The signed registration send request must bind attempt + immutable submission hash + current send generation. The verified email hook records server-keyed code digest and trusted provider UUID against that exact current generation; numeric verification checks the attempt's digest before provider consumption. Do not persist raw OTP, provider hash or provider tokens. Link proof similarly binds attempt/generation/provider identity/hash and uses a distinct registration domain/purpose. An old or mismatched callback is not reinterpreted as pilot login.

Concurrent sends may make a delivered older provider OTP unusable; fail closed and allow fresh resend without discarding local quiz. Never authorize a mismatched intent merely because the provider accepted some email-scoped OTP. Limit claimed verification attempts under the same existing budget and expiry. Actual local hook proof, not only stubbed send callbacks, must populate this binding.

Missing-only completion detects absence from raw profile, not normalizeStoredQuizAnswers defaults. Preserve valid scalp type plus NULL condition as explicit none; preserve empty concerns under existing scanner semantics. Invalid/missing scalars and empty chemical treatment are unanswered. Expose a post-auth partial answer view and missing question IDs; submit only missing answers or a complete client draft whose present fields are ignored. Server recombines authoritative present fields with allowed missing answers, validates canonical full source, then performs both-revision CAS. Do not manufacture defaults such as density=medium to avoid asking a genuinely missing required answer.

Marketing completion records the user's checkbox and exact consent source independently of authentication proof; no new campaign subscription/DOI transition. Prior R3/R5/R6 legal/provider rollout constraints remain release-package requirements. This local implementation authorizes no real user consent or data mutation.

## Boundary DTOs for parallel implementation
Main owns this contract and integration. All JSON bodies are strict, bounded and non-logging.
- `RegistrationSubmission`: `{requestId: UUID, answers: QuizAnswers, firstName: string1..100, email: normalized string<=254, marketingOptIn: boolean}`.
- `POST registration/start`: submission → `{attemptId:UUID, codeLength:8}`. Retry/resend pins exact validated hash; a changed submission receives a different client requestId.
- `POST registration/verify`: existing `authVerifySchema` → `{userId:UUID, hasExistingProfile:boolean, profileRevision:string, completionToken:string}`. Token is opaque scoped verified onboarding authority; it must not work as scanner access or ordinary auth proof. Existing profile state read only after provider proof.
- `POST registration/complete`: `{completionToken, submission, choice:'create'|'keep'|'replace', expectedProfileRevision:string}` → `{session:MobileSession, bootstrap:{status:'ready',profileRevision,contextRevision}}` or `{status:'profile_required',completionToken,profileRevision}` for explicit keep needing completion. `create` only if no existing profile; collision returns profile_conflict and requires explicit choice, never overwrites. A replay returns prior publication. Session is installed only after this acknowledgement. Completion token stays in native gateway memory; process loss requests fresh verification while existing quiz draft persists.
- `GET profile/complete`: authenticated owner → `{profileRevision:string, questions:EditQuestion[], answers:Partial<QuizAnswers>}`. Questions are missing mandatory groups only; values are owner's current answers. No caller-selected owner.
- `POST profile/complete`: `{requestId:UUID, expectedProfileRevision:string, answers:Partial<QuizAnswers>}` → `{session?:MobileSession,bootstrap:ready}`; limited-capability completion requires a returned session. Server preserves present fields and validates the merged canonical source. Error profile_conflict reloads subset; no silent overwrite.
- Publication service export `completeMobileRegistration(client,userId,email,{attemptId,submission,choice,expectedProfileRevision})` returns ready bootstrap; auth layer supplies trusted owner/email and validates completion proof+intent. Publication transaction independently checks intent verified owner/hash/expiry/receipt, writes enrollment ready atomically with shared profile/source/context and consent.
- Existing shared accounts and returning mobile-enrolled users need ordinary login/refresh/bootstrap support through the separately gated policy. Before proof, ordinary login returns a uniform attempt response and uses shouldCreateUser:false; only registration/start creates accounts. Existing static pilot routing and callback acceptance remain unchanged when registration flag is off.
