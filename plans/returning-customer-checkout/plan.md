## Designed user journey — confirmed 2026-09-13

1. An expired customer opens their old result paywall or reactivation and chooses a plan and payment method. Existing-access checks still run on the server.
2. Old paywall uses its existing email checkout, as confirmed. Reactivation uses the authenticated account. Neither sends customers to a different offer page just because they bought previously.
3. A proven missing Stripe customer is repaired under the confirmed guarded automatic-recovery option. The customer continues with the selected method; Chaarlie account history is retained. Stripe creates a replacement customer during the new subscription checkout; deleted Stripe history and payment methods are not recreated. Do not delete an account or weaken ownership checks.
4. If reactivation authentication is no longer valid, show “Bitte melde dich erneut an” / “Einloggen und fortfahren”. Sign-in returns to the same selected plan and a server-validated attempt; it never itself triggers payment. If access has meanwhile become active, return to the account.
5. If creation definitely never started and no concurrent/previous checkout exists, offer retry or another payment method. A null provider reference alone is insufficient proof.
6. If the provider outcome is uncertain, show “Bezahlvorgang fortsetzen”, reconcile/resume the same provider attempt, and withhold a second provider. Do not say no money was charged. Confirmed payment follows existing activation. If resumption remains inconclusive (including the creation-expiry boundary), show the existing pending-status pattern: “Zahlungsstatus noch offen”, “Bitte nicht erneut zahlen”, “Status prüfen” and customer-initiated “Problem melden”. Reuse the existing support lifecycle; do not add automatic outreach. Never open a second payment to escape an uncertain first attempt.

## Technical recovery contract

The existing provider lock prevents duplicates when creation succeeds but its response or database binding is lost. Keep that protection. Move deterministic identity/pricing preflight before provider claim where possible. Any late claim must revalidate reservation/access before the first side effect.

For missing Stripe customer, accept only a structured customer-specific `resource_missing`/deleted-customer result. A missing price/session or generic 404 is not permission to replace a customer. Use authenticated account identity and compare-and-set when changing a stored reference; never overwrite a concurrently changed customer ID. Preserve reservation metadata and account ownership checks through activation.

### Durable Stripe recovery protocol (reviewed; findings reconciled below)

Retries must use stable provider parameters and idempotency keys. Do not reuse an initial key with changed `customer`/`customer_email` parameters. Scope this protocol to membership reactivation; other checkout kinds keep their existing contracts.

Add one nullable, service-role-only `stripe_checkout_context jsonb` column to the existing reservation. Version 1 contains `version`, Stripe account/mode identity (no credential), authenticated account ID and email snapshot, immutable `initial_params`, optional immutable `recovery_params`, and one fixed provider expiry. Store server-constructed parameters only, never client secrets, payment details, or raw provider errors. Existing table RLS remains enabled with no public read policy.

1. Resolve current access, validated identity, price and funnel metadata before claiming. A customer retrieve is read-only preflight. First verify the intended Stripe account and live/test mode using trusted deployment configuration and provider identity. A `resource_missing` error alone does not prove deletion: an account/mode mismatch can hide a valid customer. If the exact stored customer is confirmed deleted or unusable in the verified intended account/mode, construct subscription parameters using the authenticated email instead. Unknown/mismatched provider context blocks automatic replacement and surfaces a configuration/reconciliation error. Never search Stripe customers by email to choose ownership. A non-missing lookup failure is retriable; it does not authorize replacement.
2. A new service-role `prepare_membership_reactivation_stripe_checkout` RPC locks the owned reservation and atomically claims Stripe, freezes the context, and marks `reconciliation_required` **before** external creation. It accepts an unclaimed open row, or returns an already frozen context unchanged. It rejects another provider, closed/expired rows, changed account/mode, and a legacy selected Stripe row with no context. The route must use the returned persisted params, even if the candidate built from the current profile differs. This also freezes origin, metadata, attempt ID and pricing across concurrent requests.
3. Initial creation uses `membership-reactivation:<reservation-id>:v2:initial`. Every concurrent retry uses that same persisted request. Existing provider references are retrieved before creation. A profile update, deployment change, or restarted process must not reconstruct a different request under this key.
4. If the provider account/mode remains verified and creation still returns structured `resource_missing` with `param=customer` for the **frozen** initial customer (for example deletion after preflight), a second service-role `recover_membership_reactivation_stripe_checkout` RPC locks the owned reservation, verifies version/account/mode/original-customer/no-bound-reference, and freezes recovery params once. Recovery params equal the initial params except removal of `customer` and insertion of the frozen authenticated email. It preserves the original expiry/price/metadata. The key is `membership-reactivation:<reservation-id>:v2:missing-customer`. All retries prefer this persisted recovery request once present. Concurrent original requests still reference the same now-missing customer; they cannot create a valid competing session. Reject generic 404, missing price/session, auth/provider mode errors, or conflicting ownership. No fallback from an ambiguous original outcome.
5. Bind the one resulting session through the existing compare-and-set helper; repeated binding of the same ID succeeds. A lost response/bind keeps Stripe selected and resumes that exact request. Do not clear `profiles.stripe_customer_id` before provider success: the recovery context, not a mutable profile, controls this attempt. Existing verified activation updates the actual replacement customer on the same account; add ownership/concurrent-change regression checks and require reconciliation if account mapping conflicts.
6. Bound creation to the persisted `expires_at` (use the reservation deadline). This depends on the reservation TTL remaining at most 24h, within Stripe’s maximum Session expiry; enforce the bound when building context. Do not initiate any new provider create when fewer than 30 minutes remain; a delayed request beyond this boundary fails Stripe validation with its unchanged expiry. Retry a known reference by retrieval; do not mint a fresh key when the provider idempotency retention window may have elapsed. Unbound outcomes stay reconciliation-required until their actual state is established. They do not automatically become a new purchase after a timer. When fewer than 30 minutes remain and there is no known Session reference, do not try a fresh creation or issue a new reservation: return the existing reactivation-unavailable outcome and render the explicit pending-status state described in journey step 6. Known references can still be retrieved and their actual outcome displayed. This is an acknowledged availability limit, not evidence that no earlier payment occurred.

Both RPCs must validate ownership, provider, version and terminal status, lock the row, use a fixed search path and revoke public/anon/authenticated execution. Do not accept an arbitrary user-supplied JSON blob; the route is the only caller and constructs/validates the persisted contract. Local database tests exercise all predicates and races.

Compatibility: legacy selected/null-reference reservations lack a trustworthy frozen request. Do not silently migrate them to fresh keys or unlock them. Existing known references can be reconciled; unbound legacy attempts remain same-provider recovery or operator investigation. This is an explicit limitation for attempts already in flight at rollout. A no-context open row can adopt the new protocol only under the locking RPC. Amend the legacy generic provider-claim RPC to refuse context-bearing Stripe rows, so an older deployment cannot construct a second legacy-key session during rollback. New code uses the new RPC for those rows. PayPal continues to be refused once Stripe owns the reservation.

Do not add a naive “release if provider_reference IS NULL” operation: another request can be creating a provider session concurrently. Do not automatically release on timeouts, provider 5xx, binding failure, or ambiguous database error. The first implementation should preserve the same-provider lock after provider work begins; any broader release requires an explicit exclusive-operation protocol and adversarial proof. The definitive-no-start mockup applies only before provider work and after checking no existing attempt; otherwise use the resume state.

Reuse existing route `error` values and the existing failure classifier/telemetry path; do not invent a parallel API envelope or taxonomy. Add only the scoped recovery reason/actions that existing values cannot represent, with contract tests and no PII. Scope reauthentication handling to authenticated reactivation so anonymous result checkout stays public. Check feedback/support-report enums before adding a global feedback kind; prefer scoped composition if shared persisted contracts would otherwise change.

### Authentication return contract

Only Stripe switches its request-scoped SSR client to the existing shared `createClient`; PayPal already persists refreshed cookies. Keep admin clients and other checkout-context responses unchanged. Both reactivation guards return 401 with `error: reactivation_authentication_required`; record `errorFamily: authentication` using the existing observability vocabulary.

Use a small pure return-URL builder shared by `/reactivate` and the recovery UI. It accepts a parsed `BillingInterval` and allowlisted return destination and constructs `/auth?reason=session_expired&next=<encoded /reactivate?interval=...&next=...>`. Do not put account identity/email/authority in the URL. The existing auth confirmation route independently checks same-origin navigation. This also fixes the current direct signed-out `/reactivate` redirect dropping the selected interval.

Show the reviewed explicit sign-in action in the reactivation component. Pass typed PayPal authentication failure through `PayPalSubscriptionButton` and `PaymentMethodCheckout` to that same handler. Do not create a payment-support case for authentication failure or add a global persisted feedback enum just for this state.

After login, re-run authenticated account/access checks. A 401 proves only that the failing request created nothing; a prior request may already have created a reservation. Before creating any provider object, resolve/reuse the newly authenticated user's existing reservation through the existing acquisition semantics and provider lock, using its actual provider for resume. Preserve interval/destination; exact browser attempt UUID is correlation, not authority, and need not survive login. A different account must never receive the previous account's reservation/reference; recheck eligibility for that account and require an explicit continuation. Include the existing-provider conflict in the UI recovery tests rather than leaving a generic 409 dead end.

Tests also cover `tests/auth-post-checkout-routes.spec.ts`, `tests/payment-method-checkout.test.tsx`, a focused mounted reactivation recovery test, and a mocked route response that proves Stripe actually writes refreshed cookies.
