# X1 — Multi-use products: facts (read-only, 2026-10-09)

Scope: one catalogue row per category for multi-use hair products. Evidence is file:line or live SELECT (Supabase pqdkhefxsxkyeqelqegq). No design proposals beyond one line each.

## 1. Identity model today

- `products` is the identity spine (docs/catalog-authority.md:5). Columns of note: `category_key`, `brand_id`, `product_line_id`, `origin`, `is_chaarlie_recommended`, `lifecycle_status`, `affiliate_link`, `image_url`. Unique indexes: `products_name_category_unique (name, category)` and `products_id_category_key_key (id, category_key)` -> two sibling rows may share a name only when the category differs; they may share affiliate_link/image_url freely.
- `product_identifiers` (cols: product_id, identifier_type in ean/gtin/barcode/retailer_sku/retailer_url/manufacturer_sku, normalized_identifier_value, canonical_gtin14). Unique `idx_product_identifiers_canonical_gtin14_owner (canonical_gtin14) WHERE NOT NULL` (supabase/migrations/20260826142200_product_identifier_canonical_gtin_invariant.sql:49) -> exactly one product row per GTIN. Also unique (product_id, identifier_type, normalized_value). `retailer_sku` rows are not constrained across products.
- `product_relationships` CHECK `relationship_type IN ('replaced_by','add_on_for')` (supabase/migrations/20260503123000_add_product_lifecycle_and_bondbuilder_specs.sql:19-21; TS type `ProductRelationshipType`, src/lib/types.ts:242). Live usage: 8 `replaced_by` + 1 `add_on_for` (Olaplex, bondbuilder); all 9 are same-category edges (verified live). No "same package / sibling / variant-of" type exists.
- brands/product_lines: `products.brand_id`, `products.product_line_id` (FK identity layer, docs/product-identity-normalization.md:7-9); display = `Brand · Line` + name + category chip (docs/product-catalog-identity-rules.md:17-33). The docs define identity as brand+line+clean_name+canonical_category_key and say category mismatch with otherwise exact match = review (docs/product-identity-normalization.md "Text Matching" step 4) -> by design "same name, other category" is a review case, not a sibling.
- Notion of "same physical package" across rows: NONE in schema or code. Only prose: plans/2026-08-28-remaining-barcode-resolution-rules.md:23,77 ("Unresolved physical duplicates", "one barcode owner", "Alternate use modes belong in protocols... future consolidation pass may model multi-category identity"). Sibling pairs are discoverable only by shared affiliate_link/image_url.
- Existing tombstone pattern (docs/catalog-authority.md:60): source of a `replaced_by` edge = retained identity tombstone, exempt from completeness; the audit treats it as superseded (src/lib/catalog-authority/audit-reader.ts:135-141; audit.ts:99; recommendation selection excludes sources, selection.ts:123,1105).
- Brand/line data on the pairs is inconsistent (Garnier vs "Fructis" brand on Aloe mask; "Hair Food" line on Garnier rows vs registry line "Fructis"; "L'Oréal Paris" vs "L’Oréal"; Balea vs "Balea Aqua").

## 2. Scan path

- GTIN -> product: `lookupCatalogProductByIdentifier` (src/lib/scan/identifier-lookup.ts:35-81) canonicalises to GTIN14, selects `product_identifiers.product_id`, filters active+lifecycle, returns a single `{productId, category}`. If >1 active product matches it logs `scan_identifier_collision` and returns null (lines 69-76) -> a second GTIN owner would today be treated as a miss, not a choice. Return type is a single hit (line 25-28).
- Web: src/app/api/scan/resolve/route.ts:354-425 (hit -> quarantine check -> productId/category) then :436 `decision = context.snapshot.decisions.find(entry.category === category)` and :446 `loadScanVerdictForProduct(...)`. Mobile: src/app/api/mobile/v1/scan/resolve/route.ts -> `resolveMobileScan` (src/lib/mobile/scan-service.ts:105-240; `findProduct` :373-389; `lookupMobileIdentifier` :398-428, which treats "collision/inactive" as `unavailable`).
- Verdict is per ONE category: category from the product row, decision = the user's plan decision for that category; roles are the decision's roles within the category (load-scan-verdict.ts:52-100; resolve-verdict.ts:172-221; role-selection.ts best-of-roles). Alternatives are same-category catalogue candidates (load-scan-verdict.ts:84-95). No cross-category evaluation exists.
- Payload: web `ScanResolveResult` kinds (in_catalog/not_needed/unknown/pending_submission) with a single `product` (+`categoryLabel`) (src/lib/scan/types.ts:81-82); mobile zod union `assessment|not_needed|profile_decision_deferred|submission_required|authority_unavailable|profile_required|retryable_error` with a single `product` incl. `category`/`categoryLabel` (src/lib/mobile/scan-contracts.ts:20-116, version 1). No "several candidates / choose a use" kind on either surface. Also keyed on productId: `loadScanSavedState`, wishlist, free-reveal, mobile history (route.ts:466, tables `scan_wishlist`, `scan_free_reveals`, `mobile_scan_history`), and a per-category "zweiScansGleicheKategorie" trigger (scan-flow.tsx:1127).
- Web UI: src/components/scan/{scan-flow,scan-result-card,scan-result-sheet,scan-search-sheet}.tsx render one product + category chip. iOS app lives in ios/Chaarlie (not read in detail).
- Search: `/api/scan/search` (src/app/api/scan/search/route.ts:93-123) + `matchCatalogProducts` (src/lib/scan/catalog-search.ts:131-153) match on composed brand+line+name title, no dedupe/grouping; result row shows title + `categoryLabel` (scan-search-sheet.tsx:807-815). Siblings with identical name would appear as two rows distinguished only by the category label (currently the 7 pairs have mostly differing names, e.g. "3in1" vs "3 in 1").
- Today's disambiguation of the 7 pairs is "one GTIN owner" (plan 2026-08-28 lines 69-77): Aloe -> mask row, Macadamia -> leave-in row, Balea Aqua -> mask, Guhl -> conditioner, Midnight -> oil, Pantene -> oil, Balea Tiefenreinigung -> deep-cleansing (live GTIN placement matches, except R3 findings propose Midnight owner=leave-in).

## 3. Plan double-slot

- Stage-3 chooses one product per decision (category+role); candidates are loaded per category from `products` (selection.ts, catalog-facts.ts `loadStage3RecommendationCandidatesByRole`). Dedupe found: `dedupeById` inside one candidate list (selection.ts:193) and `dedupeCapturedProducts` for repair drafts (routine-authority-repair.ts:145) only. No dedupe by brand/line/GTIN/affiliate_link/package across categories anywhere in src/lib/personal-plan or recommendation-engine -> yes, the plan can place two sibling rows (e.g. Garnier Macadamia as conditioner AND leave-in) with no check. Oil review has a same-category grouping helper only (oil-review-group.ts).
- Live evidence: no draft/routine version/portfolio currently contains both rows of any of the 7 pairs (SELECT on personal_plan_product_drafts / routine_versions / portfolio_versions). But single rows are in heavy use: Pantene leave-in `f8f3b51d` in 14 drafts / 12 routine versions; Garnier Aloe mask `52264c47` 7 drafts / 8 routines; Guhl conditioner `11d42d9d` 4 / 5; Balea Aqua leave-in `c6e80f39` 2 / 2; Aloe leave-in `0307c903` 2 / 1.
- Routine/Anwendung: routine items carry `product: owned{capturedProductId, productId} | planned{plannedPurchaseId, productId} | pending_review | none` per category slot (src/lib/personal-plan/routine/contracts.ts:91-112); presentation keyed by `productId` (contracts.ts:~175). Nothing assumes global product uniqueness, nothing prevents the same physical bottle in two slots; no "same bottle" wording/merge. Compiler merges per application, not per bottle (routines/personal-plan/application/compiler.ts:505).
- Ownership: `user_products (user_id, category, catalog_product_id)` unique where owned (index `user_products_live_catalog_identity_key`); Stage-3 owned-product creation requires `products.category_key == category` (stage3-persistence-supabase.ts:355-390 via `personal_plan_create_or_reuse_user_product`). So "I own Garnier Macadamia" = one row per (category, product); owning the conditioner row does NOT imply the leave-in sibling. Live: owned rows today sit on Aloe leave-in `0307c903` (1), Balea Aqua mask `55727898` (1), Pantene leave-in `f8f3b51d` (1) — note Aloe's and Pantene's owned rows are on the rows that do NOT own the GTIN (scan would resolve to the sibling).

## 4. Intake

- Review/approval workflow: submission has one `category`; approval requires `final.product.category_key === submission.category` (src/lib/product-intake/review-workflow.ts:53-56). Matching (product-matching.ts:255-283,440-470): an identifier hit on a product of ANOTHER category -> `pending_review` with `identifier_category_mismatch_review`, never an auto-create; same-category multiple hits -> `identifier_ambiguous_review`; text mismatch -> `text_category_mismatch_review`. `product-lookup.ts:705` returns `category_mismatch` candidates.
- Bulk apply (expansion-apply.ts:339-349, 599-609): GTIN already owned -> product parked with gap `canonical_gtin_already_owned`; `existingIdentities` dup key is `category_key|name` (line 264-266), so a same-name sibling in a different category passes the identity check but is parked on the GTIN unless the identifier is omitted. DB-side `apply_scan_expansion_batch_v1`/`product_intake_approve_reviewed_product` read back identifier sets per product (migration 20260929230000).
- No "create sibling row for an existing package" path exists (grep sibling/duplicate: only scan-submission 23505 handling submissions.ts:1005,1145 and dispositions `identity_ambiguous`). Cantu precedent: duplicate resolved by retiring (`retired_from_personal_plan / duplicate_identity`).

## 6. Category engines on multi-use

- Mask (docs/research/mask-inci/v1.0/00_category_charter.md:20,53-54,62; mask-classification-standard.md:99-140): multi-use is MODE-SCOPED — classify only the rinse-out mask mode if directions state dwell; envelope carries `multi_use: true` + `multi_use_covered_mode` + `multi_use_uncovered_modes`; "No MODE is profiled twice" (R1, 2026-09-14); ambiguous -> `multi_use_directions_ambiguity` review trigger (§2.2 step 5, §14). Cross-category multi-row architecture "parked out of scope by Nick"; parked work = "scan GTIN disambiguation, routine double-slot semantics, sibling-row intake" (charter:62; standard:138). `multi_use` is "never a quality signal / not a comparison input". Guhl, Garnier Hair Food, Balea 3in1, Isana 3in1, Balea Aqua 3in1 = eligible mode-scoped.
- Conditioner (docs/research/conditioner-inci/v1.0/00_category_charter.md:14-22; standard:45,281): EXCLUDES "multi-use formulas permitting both rinse-out and leave-on use" and masks/distinct contact-time mode; a "2in1 Kur & Spülung" is included only with one short rinse-out mode. Charter:58 declares Guhl eligible as "one immediate rinse-out mode" — conflicts with the Mask R1 ruling that Guhl has a distinct 2-3 min Kur mode. Garnier Macadamia exists as a conditioner row despite the exclusion.
- Leave-In (docs/research/leave-in-inci/v1.0/leave-in-classification-standard.md:180-187 (G1 capture rule), :1764): a dual-use direction ("im Haar lassen oder nach 2 Minuten ausspülen") keeps the record in-category, both direction sentences captured, `application_stage` from the leave-on half only, flag `dual_use_directions`, routed to human review; a sole-rinse direction = `excluded_other_form`.
- Oil decision (docs/personal-plan/categories/oil/decision.md:263,292): prefers separate products per role over a multi-use compromise (about oil roles, not packages).
- Mask category decision (docs/personal-plan/categories/mask/decision.md:228,397): multi-use behaviour belongs to product protocol; missing evidence = ordinary rinse-out only.
- Catalogue decisions already recorded for this batch: plans/catalog-completeness-fill/decisions.md:28-29 (M1 one row per category incl. scan/plan/intake; M2 manufacturer-names-the-use rule; retire Balea shampoo row, Midnight oil row, Pantene leave-in row) and research/r3-identity-cadence-duplicates/findings.md §1/§4 (keep-both: Macadamia, Aloe, Guhl, Balea Aqua; keep-one: Tiefenreinigung, Midnight, Pantene). Caveat: Pantene leave-in row `f8f3b51d` has 1 owner + 14 drafts/12 routine versions; retiring needs moving owners (existing `replaced_by` edges are all same-category).

## What must change (one line each)

- Schema: relax single-owner GTIN rule (unique on (canonical_gtin14, category) or a package/group id) + a sibling link (`package_group_id` or new `product_relationships` type; CHECK currently only replaced_by/add_on_for); expansion-apply/backfill/audit GTIN-collision checks follow.
- Scan: lookup returns a list; resolver must pick/ask a use (all categories vs. the user's plan decision) and web+mobile payload/UI need a multi-result shape; the `scan_identifier_collision` -> null behaviour must stop; history/wishlist/free-reveal are per productId.
- Search: group or label sibling rows (same package) so they do not read as duplicates.
- Plan: add cross-category same-package guard (one bottle in two slots) in Stage-3 selection/portfolio/routine, plus owned-product mapping (one `user_products` row per category; owning one row does not imply siblings).
- Intake/research: add sibling-row creation path for an existing package (identifier_category_mismatch_review currently blocks), per-category research/engines per mode.
- Engines/docs: reconcile mode-scoped Mask, Conditioner exclusion of multi-use, Leave-In dual-use; Guhl conflict between conditioner charter and Mask R1.
