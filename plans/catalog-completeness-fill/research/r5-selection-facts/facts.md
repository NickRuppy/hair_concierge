## 0. Cross-cutting facts (read first)

1. **All four adapters run the same pipeline**: candidates are loaded by `loadStage3RecommendationCandidatePool` (`AUTH/catalog-facts.ts:229`) = active + lifecycle `active` + `is_chaarlie_recommended`, ordered `sort_order, id`, then re-sorted by `compareRecommendationFacts` (`catalog-facts.ts:1273`: `catalogSortOrder` -> displayName (de) -> productId). The adapter only runs when `productFacts == null` (uncovered role, nothing owned) to produce a `recommendation`.
2. **What the evaluator receives** (`Stage3AuthorityInput`, `AUTH/contracts.ts:203-229`): `category`, `role`, `categoryDecision` (the Stage-1/Stage-2 decision: `target`, `reasons[]`, `frequency`, `executionState`, `deferredFacts`), `coverage[]`, `hairThickness`, `productFacts`, `recommendationCandidates`, `heatCarrierCoverage`, ids/fingerprints. **There is no profile object, no hair colour, no scalp sensitivity/oiliness, no chemical treatments, no wash frequency, no budget, no goals.** Those exist upstream in `InitialNeedPlanSnapshot.profile` (`src/lib/personal-plan/types.ts:133-157` `PlanProfile`) and `.assessments` (`types.ts:~236 PlanNeedAssessment`), which the gateway holds in `Stage3EvaluationContext.refinedNeedSnapshot` (`AUTH/contracts.ts:231-235`) but only `hairThickness` is copied into the input (`products/production-persistence-gateway.ts:478`; `product-previews.ts:255`).
3. **Input builders that would all need any new field** (6 call-sites build the input by hand): `products/production-persistence-gateway.ts:466-479` (Stage 3), `product-previews.ts:241-257` (Stage-1 previews), `products/fit-comparison.ts:137/318/422/442` (re-evaluations), `src/lib/discovery/equal-options.ts:42-60` (consult cockpit), `src/lib/scan/resolve-verdict.ts:205` (+ `load-scan-verdict.ts:75-121`, `src/lib/mobile/scan-service.ts:315-362`, which feed `hairThickness` from `context.snapshot.profile.hair.thickness`).
4. **Shared row-level facts for the 4 categories**: `thickness` is deliberately NOT a fit criterion (`commonUnknownFacts(..., {requiresSuitableThickness:false})`; DB `suitable_thicknesses` is `[]` for all dry shampoo + scalp care rows, `{fine,normal,coarse}` for deep cleansing + bondbuilder). Protocol readiness: every active recommended product of the four categories has `product_application_protocols` rows for its roles with a `guidance_payload` whose `scope` is `product`/own category/own product id (checked by SQL), so all count as `verified_complete`; none has `application_guidance_protocols` v2 rows.
5. **Budget / Profi tier is NOT on main.** `grep` of `src/` on main finds no budget/market-segment code in the personal-plan path; `products` has no `market_segment`/tier column in the live DB (columns listed in section 2). It exists only on branch `codex/profi-tier-baseline` (pushed to origin; commits `d8c113c6` + merge `916c28dd`, merged main #653 in): adds `products.market_segment` (`drugstore|professional`, migration `20261009140000`, backfill separate), `user_facts` domain `shopping_preferences` (Bis 5 EUR / Bis 15 EUR / no cap; strict|flexible; migration `20261009130000`), `src/lib/personal-plan/products/budget-policy.ts` (pure, applied on top of an existing fit ranking, never re-ranks by fit), `Stage3EvaluationContext.budget`, flags `SHOPPING_BUDGET_ENABLED`, `PRODUCT_MARKET_SEGMENT_DISPLAY_ENABLED` (default off). It also changes `authority/categories/bondbuilder.ts` (see 6.4). Segment proposal (`plans/profi-tier-baseline/market-segment-proposal.csv` on that branch): all dry shampoo, scalp care, deep cleansing = `drugstore`; bondbuilder = Aveda, Epres, K18, Kerastase, Olaplex, Redken `professional`; L'Oreal Elvital, OGX `drugstore`.
6. **Doc/code gap**: the confirmed category decision docs (`docs/personal-plan/categories/{dry-shampoo,scalp-care,deep-cleansing,bondbuilder}/decision.md`, status confirmed 2026-08-06) already specify richer selection than the code implements (sections 6/each category). ## 4. Precedent: how ranked categories pick (shampoo, conditioner, leave_in, mask, oil)
