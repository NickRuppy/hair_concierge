## Chosen credential contract

Alternative digest registry was compared in the gap assessment. Parent chose authenticated envelopes to avoid a second provider+DB refresh transaction and additional session-revocation policy. Do not repurpose one-hour OTP attempt rows as durable sessions or depend on private Supabase token-table layout.

1. Server-only pilot configuration requires both mobile/pilot switches, exact email+UUID pairs, exact HTTPS audience/origin, explicit environment identifier, activation expiry, active key ID and a strict map of base64url32-byte signing keys. Missing/invalid/expired configuration denies every pilot route before provider/data calls. No secrets or real UUIDs in repository. Active key signs; configured prior keys verify only until their envelope/window expiry; removal denies old envelopes. No provider signing key reuse.
2. Standard compact JWS JWT envelopes using pinned `jose@6.2.12`, `SignJWT` and `jwtVerify`, HS256 only, protected `typ=chaarlie-mobile+jwt` and allowlisted `kid`. Shared portable module `supabase/functions/_shared/mobile-credentials.ts` imports bare `jose`; Node resolves the pinned package and the send-email Deno import map resolves `npm:jose@6.2.12`. Payload has exact allowed fields: standard iss/aud/sub/iat/exp plus version, purpose (access/refresh/verification), environment, canonical email, credential, and either sid (session UUID) or attemptId (verification UUID). Require all relevant fields, authenticate before claims are used, enforce exact issuer/audience/environment and integer timestamps with bounded future clock skew. Keys are canonical base64url 32-byte values. Envelope <=8192 characters; HTTP auth body <=12288 bytes accommodates proof JSON; enclosed credentials <=4096 characters. Fixed algorithm/typ prevents algorithm confusion; resolver never loads external keys or arbitrary URLs. Payload is authenticated, not encrypted; redact it exactly like original bearer credentials. Never log bodies, Authorization, keys, codes or credential-bearing callbacks. No custom framing, hand-written MAC, or provider signing-key reuse.
3. Access expiry is min(provider access expiry, pilot deadline). Refresh envelope expires at operator-approved pilot deadline; it does not alter provider token lifetime. Every request reloads current config/cohort/window, so removal/shutdown acts on the next mobile call. No arbitrary numeric production window is selected now; synthetic tests choose explicit dates.
4. Initial verify accepts only an eligible server-owned attempt; validates provider `getUser`/returned session identity and session_id before wrapping. Mint only after single-use finish succeeds. Existing exact code/link binding and no-signup remain. Pin UUID ahead of time; email equality alone cannot mint.
5. **Link verification proof before provider consumption:** the current raw tokenHash path could consume another user's link before a post-verify identity rejection. Prepare a strictly source-aware send-email hook adapter only for the exact pilot callback scheme and eligible email/UUID. It signs a separate verification-purpose envelope binding attempt UUID, email/UUID, environment/audience, token hash and expiry (at most the existing one-hour attempt window and pilot deadline). The native callback carries this proof as the opaque tokenHash field; hosted verify authenticates it and checks its attempt against the request/server attempt BEFORE provider verifyOtp. Numeric code remains bound to the eligible server-stored email. Local raw link protocol remains only in explicit isolated-local mode. Preserve existing web message generation byte-for-byte in behavior; template code rendering and hook deployment remain activation prerequisites. Use one shared portable JOSE signer/strict envelope codec for the server and Edge function, not two subtly different cryptographic implementations.
6. Bearer unwrap requires access purpose, exact issuer/audience/environment, current pinned pair and nonexpired envelope, then provider-validates the enclosed access token and checks UUID/email and the session ID from that same validated JWT against authenticated envelope. Hosted endpoints never fall back to accepting raw JWTs. Expired tokens retain existing unauthorized/refresh flow.
7. Refresh unwrap requires refresh purpose and current pinned pair before provider call; provider-owned rotation/reuse executes on the authenticated opaque credential. Validate returned access/session UUID and email before wrapping replacement tokens. Native single-flight refresh remains. Replaying current/immediate-parent envelope follows provider's established reuse behavior for lost response; arbitrary older-token reuse fails according to provider. No custom indefinite replay cache, provider setting change or unverified session identity. Provider/timeout failure never releases a partial or foreign session. Document that verify-response loss can require reauthentication, as existing flow does; don't revoke global web sessions to clean an orphan.
8. Logout accepts only wrapped pilot access, validated same provider session, and uses local provider sign-out. No global/other-session signout. No new immediate per-session JWT revocation guarantee; provider policy plus cohort shutdown remains the chosen boundary.
9. Preserve separately explicit local mode for isolated local stack only: raw credentials are accepted only with loopback Supabase target/local callback configuration and never as a fallback when pilot config/verification fails. Tests ensure production Supabase URL cannot enter raw local mode. All ordinary defaults are disabled. Do not let caller platform/header/query choose mode.

Supabase session documentation (checked2026-09-16) describes refresh reuse interval and immediate-parent recovery: https://supabase.com/docs/guides/auth/sessions . Validate actual installed SDK/local provider behavior; no claim about deployed configuration from docs alone.
