## Server access boundaries and refresh comparison

- Gate all handlers before service-role data work. `/auth/start`: exact email before attempt creation/rate-limit identity persistence/mail; then verify pinned current email/UUID binding. `/auth/verify`: check eligible server attempt before provider verification; require exact verified UUID/email again before releasing credentials. Provider `shouldCreateUser:false` remains.
- Bootstrap/profile/edit/search/resolve/logout: validated identity plus current cohort check before context/catalog/profile/admin action. Flags/config empty or malformed fail closed. Do not borrow another customer's session for negative tests. Keep browser admission, freemium and billing flags unchanged.
- Existing attempts are one-hour OTP records; resend can delete consumed records (`20260912103630_mobile_auth_attempts.sql:1-30`). They do not bind opaque refresh token/session identity, so an attempt ID or client-submitted UID cannot authorize refresh.
- Present refresh calls provider before owner lookup (`auth/refresh/route.ts:16-25`). Checking owner afterward still rotates an unrelated token and violates the proposed before-side-effect boundary. Requiring an access token alone does not prove an arbitrary supplied refresh token belongs to it. Avoid relying on private provider table internals.

Two valid architecture directions, for parent choice during hardening:

| Direction | Easier / harder | Residual boundary |
|---|---|---|
| **Recommend first: authenticated mobile credential envelopes** | Wrap each provider access/refresh credential server-side with version, purpose, environment/audience, pinned owner, provider session ID and authenticated token bytes. Verify signature and current cohort before unwrapping/provider use; revalidate returned identity/session before reissuing. Native client already treats both token strings as opaque (`MobileClient.swift:8-9,201-242`), so no new client identity system is needed. Needs a dedicated server signing-key/version/rotation contract and explicit size/logging tests. | Preserves provider-owned rotation/reuse and avoids provider+registry atomicity. Wrap bearer access too so mobile logout cannot be invoked using a separate web JWT. No new independent per-session revocation policy is implied; rely on provider logout and cohort kill switch unless stricter immediate revocation is required. This is a proposed use of standard authenticated encoding, not a bespoke cryptographic primitive or a verified implementation. |
| Private mobile refresh-digest/session registry | Gives explicit pilot-session membership/revocation/audit; no token plaintext in DB. Requires claim/CAS generation, serialized rotations and expiry cleanup, plus provider-success/DB-failure/lost-response recovery. | More distributed lifecycle state. Define whether old/current-parent retry recovers or reauthentication is required on indeterminate state. A registry alone does not make provider+DB writes atomic. Use it if independently revocable mobile sessions are an explicit requirement. |

Immediate reauthentication instead of refresh is mechanically smaller but changes the persistent-login experience; not the recommended silent default. Current Supabase docs describe short-lived access tokens, refresh rotation, a reuse interval and immediate-parent recovery for lost responses: https://supabase.com/docs/guides/auth/sessions . A stale-token strategy must respect that behavior; no project-wide auth-setting change is proposed. Changelog was checked for relevant changes; no provider migration is performed.

Code and link remain the intended pair. Current server always requires callback/emailRedirectTo (`auth.ts:77-86`), and DEBUG native parser supports `chaarlie-local://auth` (`KeychainSessionStore.swift:50-84`). Lack of Associated Domains therefore does not logically force code-only.
