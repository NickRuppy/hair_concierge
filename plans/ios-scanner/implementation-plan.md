## Chosen direction

- Swift + SwiftUI, in `ios/Chaarlie/`, committed Xcode project, local Swift package lockfile; existing TypeScript recommendation/quiz authority stays on the server. Native system camera barcode capture with AVFoundation; fixtures for simulator/UI checks, real-device camera checks before release.
- Versioned native API under `src/app/api/mobile/v1/`, sharing domain services with existing web routes. Validate bearer session using Supabase server validation, derive the user ID server-side, enforce completed-profile admission independently of paid access. No service keys in the app and no direct client writes to protected database tables. Native scanner capability is authenticated + completed profile + ready context; creating a context never writes billing/access/enrollment records or grants paid access. Existing web subscription/field-test/partner guards stay in force, using the current merged access contract for `/scan`, `/api/scan`, `/profile` and `/api/profile`; shared data is not a new web entitlement.
- Server-owned scanner evaluation context for free users. The completed B0 audit confirms shared computation but incompatible general-purpose free-snapshot writes. Implement the planned versioned scanner-context publication contract and common scanner loader; do not duplicate profile or assessment authority. Reuse existing deterministic engines; do not call paid Stage-1 admission/persistence just to enable scanning. Resolve native and web scanner context consistently; do not grant Personal Plan access or rewrite paid routines.
- No native Merkliste screen, bookmark, save/remove endpoint or wishlist membership in native results. Existing web lists and routine operations stay unchanged; account deletion still covers existing web-owned data.
- Direct APNs push plus existing Customer.io transactional-email transport, backed by durable per-channel delivery state. No new push aggregator, marketing automation vendor or analytics SDK is assumed.

## Authoritative service contracts

Exact names below are proposed new implementation interfaces; existing files above establish the source behavior. Freeze DTOs in `src/lib/mobile/contracts.ts` with runtime validation and versioned JSON fixtures consumed by Swift decoding tests.

1. **Auth attempt:** anonymous rate-limited start accepts email and optional opaque completed-quiz claim. Sender pairs one code and one login link for the same auth attempt, not two independent grants. Opaque link GET does not consume authentication; installation fallback keeps reference without exposing a session. Code/link verification is POST, one-use, expiry-bound; avoid PKCE relying on a verifier from the website surviving app installation. Prefer the existing Supabase token/hash mechanism through a server-owned attempt facade; never place raw credentials or OTP values in logs, analytics, redirect query trails or referrers. Return a session only after account identity is verified; profile readiness is a separate typed response. Unknown email without completed quiz has no scanner admission and routes to quiz after verified identity, without public email-account enumeration.
2. **Bootstrap:** authenticated user → `{status: ready|quiz_required|profile_conflict|temporarily_unavailable, profileRevision?, contextRevision?}`. Only explicit accepted quiz replacement writes over an existing profile. Previously unanswered refined questions do not force a paid quiz; under confirmed D2 retain applicable user-provided inputs, discard stale assumption-derived inputs and resolve current deterministic defaults with provenance. If no safe supported target can be produced, use D3 rather than inventing a value. Own profile/loading error never becomes `quiz_required`. Claim completion is retryable with the same user/claim id; another user's source is rejected. Empty-account native completion and explicit edit atomically publish profile plus evaluated scanner context after successful server validation.
3. **Scanner context:** immutable source hash/version, engine version, owner, relevant normalized basic/refinement answers and derived `NeedPlan`. Use server-managed context persistence and an owner head pointer through the planned common scanner loader; B0 verified that the parked free-snapshot writer does not supply this safe edit contract. Reuse pure computation and source adapters; no paid-plan or routine writes. D2 source precedence: before a native edit, use a valid current refined snapshot, otherwise a valid initial snapshot, otherwise derive from the completed regular quiz. After an explicit profile edit, its atomically published context is authoritative for both scanners; old paid snapshots cannot override it. A later paid/refinement publication may replace scanner context only if its source basic-answer revision/hash matches the current shared profile; otherwise keep the current scanner context and expose/reconcile a source conflict rather than silently rolling back answers. Retain only applicable user-provided advanced inputs and recompute assumed inputs. Use DB revisions/source hashes, not wall-clock last-write-wins. Test concurrent web refinement and native edits. Paid plan/routine storage and access are unchanged. Missing context can be provisioned idempotently from an eligible completed source; source lookup failure returns retry, never speculative defaults.
4. **Resolve:** request barcode or canonical product ID → discriminated `assessment|not_needed|profile_decision_deferred|authority_unavailable|submission_required|submission_pending|profile_required|retryable_error`. `assessment` has canonical product identity/image/brand/category/price and allowed purchase URL; authority verdict; ordered criteria with labels, product values, target values, state, axis kind, definition, category-fit text; at most five eligible alternatives of the same display contract without recursively nested alternatives; context revision. The current `not_needed`/`deferred` outputs remain distinct authority outcomes. Confirmed D3: unavailable user-target evaluation shows a short reason and a dismissal back to scanning, without an additional-question flow or catalog-research submission. A known not-needed verdict must not be relabeled as missing information. All ten scanner categories have policies; “unsupported” here describes invalid/unavailable target state, not necessarily an unsupported product category. Never send missing-user-target or paused scalp decisions to catalog research. Authority status `unknown` plus machine-readable missing product facts is the research trigger, not the public generic `unknown` string. Technical invalid-target/read failures stay retryable/non-research; no known fit verdict is fabricated.
5. **Presentation:** generated deviation line from all nonpass rows, with complete set values; all pass = `Alles im Ziel.` No fabricated cadence/advice. Product truth comes from typed catalog facts; table labels are a presentation mapping, never mutate catalog truth to fit a cell. Numeric prices compare only in the same currency; unknown/incomparable prices sort last within verdict tier, stable product-ID tiebreak. For the approved native carousel the total order is verdict (ideal then supportive), numeric price ascending within the verdict, then stable product ID; unknown/incomparable price last. Native display ranking intentionally omits web coverage/caution/catalog/authority-pin tiebreaks while preserving each product's actual authority verdict and facts. Select max five from the full eligible evaluated pool after this ordering, not by reranking an already truncated top three. This is the reviewed design's presentation rule, not a change to category recommendation authority. Add an explicit native selection policy/limit; retain the shared constant and default web comparator/max3 unchanged.
6. **Submission/notification:** canonical barcode/category, opaque owner-bound submission ID, source `ios_scanner`/approved organic provenance recorded alongside existing intake source. Race-safe reuse existing open submission. A product rework case must not deduplicate straight back to the unusable product. Readiness event uses the same public product-completeness/supported assessment gate; submission + result version + channel unique key, independent email/push jobs, server claim lease/attempts/receipt/retry. Do not reuse the chat-only `notification_sent_at` bit. Registry binds APNs token, installation, environment and current account; revoke on logout/switch/delete, remove invalid tokens. Retry one channel independently; email never depends on APNs success. Worker rechecks ownership, account state and product eligibility before sending. Authenticated deep links resolve ownership and CURRENT profile, not stale verdict copy or an email possession grant. A withdrawn result opens a recoverable unavailable state, never an obsolete buy link.
7. **Account changes:** Supabase secure email change through verified current session and required confirmations; no account merge; conflicting email rejected; shared account data ownership remains the immutable UID. Reconcile email-keyed Customer.io identities and their consent/subscription state after verified changes, without creating a fresh marketing identity or merging an unrelated account; old addresses must stop receiving account notifications. Deletion request requires recent verified user intent, locks sensitive app writes and journals provider IDs before cascades. Cancel future renewals of every active web subscription, verify provider truth; unknown/failure keeps operation pending and billing linkage intact. No refund implied. Then scrub/delete personal data and revoke sessions with an account-state guard against still-valid JWTs; an open support case alone must not keep hair/profile/list data or the app account alive. Preserve a minimal independent case record/contact under the existing retention policy, permitting only necessary case/deletion communications after deletion; marketing and scan notifications remain suppressed. Distinguish this from unresolved cancellation of future renewals, which still needs safe provider reconciliation; preserve only established required records under a reviewed non-cascading retention mapping. Completion and partial/pending states remain distinguishable.

No promised research duration. 6. **Profile:** raw saved answers; full prefilled quiz edit; commit only when profile and derived scan context publish successfully. Abandon leaves old answers. Refresh scanner assessments after success. D2 governs detailed existing users. Email change is verified; logout clears local account data. Help opens `info@chaarlie.de`; privacy/imprint use existing public pages.
