**Blockers** (will regress/mis-ship as written — both are legal-adjacent, § 356 BGB withdrawal consent)
1. **`custom_text` is not allowed for `ui_mode: 'elements'`, and that's where the required consent text currently lives.** The § 356 BGB immediate-access/withdrawal-waiver copy exists *only* in `custom_text.terms_of_service_acceptance` — `src/lib/stripe/checkout-session-params.ts:37–42`. The installed SDK documents the constraint (`node_modules/stripe/esm/resources/Checkout/Sessions.d.ts:2092`, "You can't set this parameter if `ui_mode` is `custom`"; `custom` was renamed to `elements` per the SDK CHANGELOG). The plan frames this as conditional — *"if Stripe rejects current `custom_text` … in Elements mode"* (plan:262) — when it is a knowable certainty. Fix: stop hedging; the plan must commit to an app-owned consent surface **and specify how acceptance is enforced before `confirm()` and recorded** (audit trail), not merely where it's "placed." (The Task-1 red test partly guards this, so it won't silently ship *if* the task is honored — but the enforcement/recording contract is undefined.)
2. **No mechanism gates the native Apple Pay sheet on the consent checkbox.** The mockup renders a consent checkbox above Apple Pay that must be ticked (`plans/mockups/2026-07-27-apple-pay-express-checkout.html:522–531`), but the plan's mechanism list (plan:136–137) only names `checkout.confirm(...)`. The native Apple Pay button can't be "disabled" — you must use `ExpressCheckoutElement`'s `onClick` event and withhold `resolve()` / surface validation when consent is missing (`node_modules/@stripe/react-stripe-js/dist/react-stripe.d.ts:376`). Followed literally, a subagent would ship a consent box the wallet ignores, letting a customer pay via Apple Pay without accepting the § 356 waiver. Add the `onClick`-gate to the adapter spec (Task 2).
