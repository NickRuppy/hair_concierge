# Hair Tools — spec token → production field mapping

## Why this document exists

`decision.md` and `conditional-guidance-matrix.md` were written against a quiz
vocabulary that no longer ships (root cause **R1**). Every rule therefore required
the implementer to invent a spec-token → production-field translation on the fly,
and those inventions diverged across files.

This file is the authoritative bridge. It enumerates **what production actually
stores**, then states the ruling for each spec token against that reality.

**Reading rule.** Where the ruling column gives a mapping, that mapping is
normative once ratified — `decision.md`, the matrix and the code must all use it.
Where the ruling column says `DECISION REQUIRED`, the spec asks for a distinction
production cannot express; nothing may be implemented against that token until
the named decision is settled. No row guesses.

**Ruled 2026-08-24.** Nick settled all nine gates `D1`-`D9`
(`plans/2026-08-24-hair-tools-d1-d9-rulings.md`). Every row that read
`DECISION REQUIRED (D1)`, `(D2)`, `(D3)`, `(D4)`, `(D6)` or the heat-protection /
`fingers` / `manageability_styling` D9 candidates now carries the ruling instead
and is normative. Rows still marked `BLOCKED — no input` or
`NOT APPLICABLE (Phase 2 catalog)` are unchanged: they wait on a capture question
or on the catalog, not on a decision.

## 5. Divergences found while mapping, not on the existing findings list

These are recorded here because the mapping exposed them; they are **not**
re-reviews of the implementation and each is a spec-fidelity issue.

1. **`tools.styling.reported_straighten` and `tools.styling.reported_curl_wave`
   are emitted together, on both families, unconditionally.**
   `routes.ts` sets `ruleIds: ["tools.styling.reported_straighten",
"tools.styling.reported_curl_wave"]` on the `not_needed` branch for _both_ the
   heated and heatless drafts. A user who reported only a heatless band receives
   `tools.styling.reported_straighten` on a `heatless_volume_set` route. The two
   spec rules have different triggers and different families. Fixture rows for
   42, 45, 46 and 8 must assert the rule-ID set exactly.
2. **`dryingRoutes = []` has no spec rule and is silently read as air-drying.**
   `[]` is a reachable completed answer. It means "none of these", which is not
   the same claim as `air_dry`, yet it lands in the `air_dry` optional branch.
3. **Mixed `dryingRoutes` sets have no spec rule.** `[air_dry,
ordinary_blow_dry]` is a valid answer the spec's single-valued
   `drying_method` cannot describe.
4. **Production already reads `diffuser_or_airflow_shaping` as airflow-shaping**
   (`STAGE2_HEAT_EVENT_DEFINITIONS`), and asks a heat-protection question for it.
   The Tool code reads the same answer as diffuser-only and A11 tiers heat
   protection differently for the two readings. Two shipped modules disagree
   about one stored value. Direct evidence for **D2**.
5. **A fourth volume-direction predicate exists.** The handoff names three
   (spec/H08, `normalization.ts`, Tools). `src/lib/personal-plan-quiz/offer-adapter.ts:172`
   `volumeGoal()` is a fourth, reading `thickness`, `density` and `texture`, and
   it can return `null` — a state neither of the other two can express.
6. **`tools.night.optional_strong` was unreachable for V2 profiles.**
   `V2_CONCERN_MAP` sends `breakage_or_split_ends → split_ends` only, so
   `concerns ∋ breakage` is impossible for `quizVersion === 2`. **RESOLVED
   2026-08-24 (`R4`): the strong trigger is extended to `breakage` or
   `split_ends`**, so V2 profiles reach the tier again (fixture 15 variant (b)).
7. **`additionalHeatTools` is silently overridden by an answered Tool page.**
   The spread `{...projectToolInventoryFromCareFacts(care), ...inventory}`
   replaces the whole family. `decision.md` states a precedence rule for drying
   only.
8. **`decision.md` describes an eight-checkbox overview; production ships four
