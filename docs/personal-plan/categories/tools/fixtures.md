# Hair Tools — table-driven fixtures

## Purpose

The 123 fixtures in `decision.md` are prose and none is executable (root cause
**R2**). This file restates them as one row per fixture, using **only production
field names and values** as defined in `input-mapping.md`.

This is the future test oracle. Precision beats coverage: a row is only filled in
where the spec unambiguously determines the answer **and** production can express
the input. Everything else is marked `BLOCKED` with the decision or workstream it
waits on.

**Updated 2026-08-24 for the `D1`-`D9` rulings**
(`plans/2026-08-24-hair-tools-d1-d9-rulings.md`). Rows previously marked
`BLOCKED — D1 | D2 | D3 | D4 | D5 | D6 | D7 | heat-protection decision` are
unblocked and carry their ruled expectation; where a row had two blockers, only
the remaining one is shown. Two fixtures are **retired**. Fixture numbers are
never reused or renumbered.

## How to read a row

- **Input** is a delta against the base profile `P0` below. Only the named fields
  differ.
- **Expected tier / lead form / ownership** describe the `PlanToolRoute` and the
  `ToolAsset` the route produces. `—` means the route must not exist at all.
- **Rule IDs** is the **exact set** the route must carry, not a subset. Several
  known defects are only visible as an exact-set assertion.
- A row tagged **`asserts divergence`** is expressible today and **currently
  fails**: the expected value is what the spec says, and the note records what
  the implementation does instead. These rows are the WS2 acceptance criteria.

## Standing note: the care→inventory projection

`projectToolInventoryFromCareFacts` derives inventory from care answers before any
rule runs. Three derivations are load-bearing for these fixtures and are **not
stated in `decision.md`**:

- `dryingRoutes ∋ ordinary_blow_dry | diffuser_or_airflow_shaping`
  ⇒ `inventory.airflow = ["hair_dryer"]` — **reporting the behaviour reports the
  device**.
- `dryingRoutes = ["air_dry"]` ⇒ `inventory.airflow = []` — an explicit
  "you own no dryer" the user never said.
- `towel.material = "frottee"` ⇒ `inventory.drying_textiles = []` — likewise.

**Ruled 2026-08-24 (`D4`).** The derivations are **kept** — the ruling creates no
new unknowns — but they are no longer allowed to state ownership the user did not
assert. Every route carries two independent facts: `reportedOwnership`, written
only from an actual user answer or marked **`derived`** when projected from a care
behaviour, and `coverage`, which is what suppresses acquisition. So derivation 1
yields `reportedOwnership = owned_generic (derived)` and may be phrased
behaviourally („Du föhnst — nutze deinen Föhn"); derivations 2 and 3 must **not**
be written as `explicit_none` at all — the user reported air-drying and a terry
towel, and that is what is stored. Below, a `(derived)` suffix in the ownership
column marks a projection rather than a stated answer.

**Notation, aligned to the WS1 contract (2026-08-25).** The ownership column uses
exactly the `contracts.ts` value domains: `state ∈ {unknown, explicit_none,
owned_generic, selected_exact, owned_exact, catalog_gap}` with
`provenance ∈ {reported, derived}` and `provenance = null` **iff** the state is
`unknown`, and `forms` empty **iff** the state is `unknown` or `explicit_none`.
A plain state name in the column means `provenance: reported`; the `(derived)`
suffix means `provenance: derived`. Derivations 2 and 3 therefore cannot be
written at all as an ownership state that asserts absence: the behaviour ("ich
lufttrockne", „Frottee") is stored as the care answer it is, the route's
`reportedOwnership.state` stays **`unknown`** with `provenance: null` — the
contract forbids a provenance on `unknown`, and air-drying is not a claim about
owning or not owning a dryer — and every suppression consequence lives on
`coverage`. The reported terry towel likewise stays a towel-material answer; it is
never re-encoded as „owns no drying textile".

## 10. Test discipline this table must be wired into

Per the handoff's non-negotiables for WS2:

1. Every row above becomes a table-driven case. A rule is not implemented until
   its row passes.
2. Rows tagged `asserts divergence` must be **red before the fix and green
   after** — they are the proof that WS2 changed behaviour.
3. Lead-form rows — 57 and fixture 59 variant (b) for `B02`, 14 and 81 for
   `W02`, 95 and 96 for `N02`, and 75 for `C02` — must assert the **rendered**
   `ToolAsset.productTypes[0]`, not `PlanToolRoute.recommendedProductTypes[0]`.
   The C1 defect survived because the route layer was asserted, before the
   projection reordered it. **`D6` (2026-08-24) makes this binding:** route order
   is authoritative and no downstream dedup, merge or projection may reorder it,
   with an order-stability assertion in `buildToolPlan` beside these seven rows.
4. Rule-ID rows assert the **exact set**, not a subset. Fixtures 8, 42, 45 and 46
   only fail as exact-set assertions. For a choice-group row the exact set is
   asserted **per member route** (35, 36, 47, 48): a `ToolChoiceGroup` carries no
   rule-ID field.
5. Occurrence rows (54, 17, 120) assert the Anwendung projection per
   `ApplicationDayTypeKey`, not just the presence of a `ToolOccurrence`.
6. **The `D8` schema-snapshot test.** A build-time snapshot of the persisted
   refinement answer keys must **fail the build** whenever a key is added,
   renamed or removed without a path-version bump — the enforcement half of the
   `D8` standing rule, and the reason the „Nur Finger" key (`fingers`), the
   drying-question change and the `R1` diffuser change cannot land silently.
   Its runtime companion is fixture 125: a row completed under an older contract
   still loads complete, and the values its contract no longer allows are ignored
   on read rather than re-interpreted.
