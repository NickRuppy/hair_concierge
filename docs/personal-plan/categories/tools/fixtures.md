# Hair Tools — table-driven fixtures

## Purpose

The 123 fixtures in `decision.md` are prose and none is executable (root cause
**R2**). This file restates them as one row per fixture, using **only production
field names and values** as defined in `input-mapping.md`.

This is the future test oracle. Precision beats coverage: a row is only filled in
where the spec unambiguously determines the answer **and** production can express
the input. Everything else is marked `BLOCKED` with the decision or workstream it
waits on.

## How to read a row

- **Input** is a delta against the base profile `P0` below. Only the named fields
  differ.
- **Expected tier / lead form / ownership** describe the `PlanToolRoute` and the
  `ToolAsset` the route produces. `—` means the route must not exist at all.
- **Rule IDs** is the **exact set** the route must carry, not a subset. Several
  known defects are only visible as an exact-set assertion.
- A row tagged **`asserts divergence`** is expressible today and **currently
  fails**: the expected value is what the spec says, and the note records what
  the implementation does instead. These rows are the WS2 acceptance criteria.

## Standing note: the care→inventory projection

`projectToolInventoryFromCareFacts` derives inventory from care answers before any
rule runs. Three derivations are load-bearing for these fixtures and are **not
stated in `decision.md`**:

- `dryingRoutes ∋ ordinary_blow_dry | diffuser_or_airflow_shaping`
  ⇒ `inventory.airflow = ["hair_dryer"]` — **reporting the behaviour reports the
  device**. Ratify or remove.
- `dryingRoutes = ["air_dry"]` ⇒ `inventory.airflow = []` — an explicit
  "you own no dryer" the user never said.
- `towel.material = "frottee"` ⇒ `inventory.drying_textiles = []` — likewise.

All three feed **D4** (ownership vs coverage).

   its row passes.

   `ToolAsset.productTypes[0]`, not `PlanToolRoute.recommendedProductTypes[0]`.
